# Технічне завдання: «We Charge» — календар активності горіння (MODIS + VIIRS)

Контекст: NASA Space Apps Challenge 2026, челендж «Harmonization of MODIS and VIIRS Hot Spots».
Джерело вимог: https://www.spaceappschallenge.org/2026/challenges/modis-and-viirs-hot-spots/
Статус документа: чернетка v0.1 (14.11.2026). Пункти зі знаком ⚠ потребують рішення команди.

---

## 1. Мета і призначення

Створити веб-застосунок, який об'єднує (гармонізує) записи активних пожеж/hotspot-ів супутникових сенсорів **MODIS** (Terra/Aqua, з 2000 р.) і **VIIRS** (з 2012 р.) у єдиний часовий ряд та показує на його основі **календар активності горіння** для довільної області інтересу (AOI).

Застосунок має дати змогу швидко побачити:
- у які місяці й роки в області було найбільше пожеж;
- як поточний місяць порівнюється з історичною медіаною;
- де є аномалії відносно багаторічних значень.

## 2. Цільова аудиторія

Служби раннього попередження й реагування, науковці, землекористувачі, пожежники. Користувачі нетехнічні: інтерфейс має бути зрозумілим без навчання.

## 3. Обсяг (scope)

**У межах проєкту**
1. Збір і нормалізація даних FIRMS (MODIS, VIIRS).
2. Гармонізація в єдиний ряд кількості hotspot-ів.
3. Веб-застосунок: вибір AOI та дат, календар, аналітика, експорт CSV.

**Поза межами** (якщо не вирішено інакше)
- Прогноз пожеж, оцінка вигорілих площ, аналіз диму.
- Акаунти користувачів, сповіщення, мобільний застосунок.
- Обробка сирих знімків (використовуються лише готові hotspot-продукти).

## 4. Дані

| Параметр | Значення |
|---|---|
| Джерело | NASA FIRMS (Earthdata): https://firms.modaps.eosdis.nasa.gov |
| Доступ | Архівні CSV-завантаження та/або API з `MAP_KEY` (безкоштовний, за email) |
| MODIS | `MODIS_SP` (архів), з 2000 р., ≈1 км |
| VIIRS | `VIIRS_SNPP_SP` (з 2012 р., 375 м); ⚠ додатково `VIIRS_NOAA20_SP`, `VIIRS_NOAA21_SP` |
| Актуальність | `*_NRT` для свіжих днів (майже реальний час) |
| Ключові поля | `latitude`, `longitude`, `acq_date`, `acq_time`, `satellite`, `instrument`, `confidence`, `frp`, `daynight` |

Обмеження: дотримуватись умов використання даних; API має ліміт запитів (≈5000 за 10 хв), тому парсер повинен вміти відновлюватись і не дублювати завантаження.

Відомі відмінності сенсорів, які потрібно врахувати: роздільність (1 км і 375 м), `confidence` (MODIS — число 0–100, VIIRS — `l/n/h`), різний час прольотів, різна чутливість до малих пожеж.

⚠ Охоплення: весь світ чи обрані регіони (напр., Україна/Європа). Впливає на обсяг даних і час початкового завантаження.

## 5. Гармонізація

### 5.1 Вимога
Після гармонізації для довільної комірки простору й місяця значення не залежить від сенсора: ряд безперервний з 2000-х до сьогодні.

### 5.2 Пропонований метод (базовий)
1. Нормалізувати записи до спільної схеми; відфільтрувати за якістю (правило фільтра за `confidence` документувати; ⚠ значення порогів).
2. Агрегувати в просторову сітку (⚠ крок 0.25° або 0.5°) × місяць окремо для MODIS та VIIRS.
3. На періоді перекриття (з 2012 р.) оцінити перехідні коефіцієнти MODIS → VIIRS-еквівалент (відношення або регресія; за потреби окремо для регіонів/біомів/сезонів).
4. Застосувати коефіцієнти до MODIS-ряду для періоду до 2012 р.; для періоду перекриття та після нього використовувати VIIRS.
5. Зберегти як сирі, так і скориговані значення, щоб можна було перевірити результат.

### 5.3 Валідація
- Графік «до/після» для вибраних регіонів на періоді перекриття.
- Метрики узгодженості (кореляція, відхилення медіани) між MODIS-скоригованим і VIIRS.
- Опис обмежень методу в інтерфейсі й документації.

## 6. Функціональні вимоги

| ID | Вимога |

| FR-2 | Гармонізований набір даних за методом з п. 5 |
| FR-3 | Вибір AOI: малювання полігона/прямокутника на карті **та** ввід координат (lat/lon) |
| FR-4 | Вибір діапазону дат |

| FR-6 | Порівняння поточного місяця з історичною медіаною AOI (у підказці клітинки календаря: медіана на цю дату, % від неї, місце серед таких самих місяців) |

| FR-12 | Підказка про методологію: що гармонізовано і яке джерело даних |

## 7. Нефункціональні вимоги

- **Доступність**: кольорові шкали безпечні для дальтоніків (напр., viridis/cividis-подібні), не лише колір як носій інформації, достатній контраст, клавіатурна навігація.
- **Швидкодія**: календар і аналітика по AOI відображаються за кілька секунд; для цього використовуються попередньо агреговані таблиці, а не обчислення по сирих точках на льоту.
- **Масштаб**: CSV-експорт великих вибірок стрімінгом, з обмеженням розміру/попередженням.
- **Відтворюваність**: парсер і гармонізація запускаються однією командою; кроки та параметри задокументовані.
- **Мова інтерфейсу**: англійська (за замовчуванням) та українська з перемикачем.
- **Безпека**: секрети не в репозиторії. Скрипти даних у `parser/` беруть `MAP_KEY` зі змінної `FIRMS_MAP_KEY` або з `parser/.env`. Ключ, збережений в адмінці (зашифрований `APP_KEY`, запасний варіант — `FIRMS_MAP_KEY` у `web/.env`), використовує лише перевірка ключа в адмінці.

## 8. Архітектура

```
FIRMS API/CSV ──► parser (Python) ──► БД (сирі точки + агрегати)
                                          │
                                  Laravel API (web/)
                                          │
                              SPA (Vite): карта, календар, графіки, CSV
```

Компоненти (вже є каркас у репозиторії):
- `docker/` — nginx, php-fpm 8.4, БД, node (Vite).
- `web/` — Laravel 13: REST API + SPA.
- `parser/` — Python-парсер і скрипти гармонізації (поки порожній).

**БД**: PostgreSQL 17 + PostGIS (у `docker-compose.yml`).

**Адмінка** (`/admin`, Filament 5): MAP_KEY FIRMS з перевіркою, довідник продуктів FIRMS (підписує рядки журналу), ліміти публічного API, журнал `ingest_runs`, швидкі області, керування адмінами. Акаунти є лише для адмінів, публічна частина без реєстрації.

Адмінка не керує завантаженням даних (див. рішення з п. 12.8): парсер не читає її налаштувань, а вона не запускає парсер. Звідти до адмінки йде лише журнал: `restore.sh` пише в `ingest_runs` рядок на кожне джерело при кожному розгортанні пакета.

### 8.1 Модель даних (орієнтовно)
- `hotspots` — сирі точки: id, sensor, satellite, lat, lon, geom, acq_at, confidence_norm, frp, daynight.
- `grid_monthly` — агрегат: cell_id, year, month, sensor, count_raw, count_harmonized.
- `harmonization_params` — коефіцієнти переходу (регіон/сезон, версія методу).
- `ingest_runs` — журнал розгортань пакетів даних (джерело, період, статус, кількість записів); пише `restore.sh`.

### 8.2 API (орієнтовно)
- `POST /api/calendar` — AOI (GeoJSON або bbox) + діапазон дат → матриця місяць × рік, медіана, аномалії.
- `POST /api/summary` — ключові показники, рейтинги.
- `POST /api/export/csv` — стрім CSV hotspot-ів за AOI і датами.
- `GET /api/meta` — доступний період даних, версія методу гармонізації.

## 9. Інтерфейс (SPA)

1. Карта (Leaflet/MapLibre) з інструментом малювання AOI та полями lat/lon.
2. Панель дат.
3. Календарна теплокарта (місяць × рік) з легендою та підказками.
4. Порівняння «поточний місяць vs медіана» в підказці календаря і графік аномалій.
5. Рейтинг найактивніших місяців/років.
6. Кнопки експорту (CSV, зображення).
7. Розділ «Про дані й метод» (прозорість гармонізації).

## 10. Критерії приймання

1. Для довільного AOI й діапазону дат застосунок повертає календар без розриву між MODIS і VIIRS.
2. Значення поточного місяця коректно порівнюється з історичною медіаною AOI.
3. CSV відповідає вибраним AOI й датам (перевірка вибірково на кількості записів).
4. Кольорові шкали проходять перевірку на дальтонізм і контраст.
5. Метод гармонізації задокументований, є графіки валідації на періоді перекриття.
6. Проєкт піднімається за інструкцією з README (`docker compose up`) і даними для демо.

## 11. Етапи

1. **Підготовка**: рішення по ⚠ пунктах, `MAP_KEY`, вирівнювання БД.
2. **Дані**: парсер, завантаження вибраного охоплення, схема БД.
3. **Гармонізація**: агрегація, оцінка коефіцієнтів, валідація.
4. **API**: календар, підсумки, експорт.
5. **SPA**: карта/AOI, календар, графіки, експорт.
6. **Доведення**: доступність, продуктивність, документація, демо-сценарій і презентація для журі.

## 12. Відкриті питання (⚠)

1. Охоплення даних: світ чи регіони.
2. Які саме продукти VIIRS (лише S-NPP чи також NOAA-20/21).
3. Крок сітки й пороги `confidence`.
4. Метод переходу: простий коефіцієнт чи регіональний/сезонний.
5. ~~Мова інтерфейсу~~: EN + UA.
6. ~~Остаточний вибір БД~~: PostgreSQL + PostGIS.
7. Перевірити вкладку Resources челенджу перед хакатоном: організатори можуть додати ресурси.
8. ~~Як парсер отримує налаштування з адмінки і як адмінка запускає завантаження~~: на час хакатону ніяк, і це свідоме рішення. Парсер бере `MAP_KEY` з `FIRMS_MAP_KEY` або `parser/.env`, продукти — зі свого коду, країни — з аргументів `export_dump.py`. Завантаження й оновлення NRT запускаються вручну або з cron за `parser/docs/deploy.md`. Адмінка показує журнал `ingest_runs`, який пише `restore.sh`. Керування завантаженням з адмінки (черга, кнопка «оновити NRT») не входить у вимоги челенджу й лишається на потім.
